## 核心认知

### 1. 产品系统四层架构（今日最重要的产出）

自己推导出的分层框架，加上安全层后：

```
数据层（Data）
  RPC → 链通信接口
  索引器 → 链上事件结构化查询
  预言机 → 链下数据上链
  向量库 → 语义搜索
  项目文档 → 知识源

编排层（Orchestration）
  Prompt → 接口设计
  Context → 信息空间分层
  RAG → 证据链
  Agent Workflow → 执行循环

执行层（Execution）
  工具调用 → 权限扩展
  钱包 → 签名/授权
  Smart Account → 受限权限
  合约交互 → 链上写入

安全层（Security）→ 横贯所有层
  Guard → 操作前的权限检查
  Simulation → 执行前预览结果
  权限策略（Policy）→ 规则引擎
  人工确认 → 关键写入节点的拦截
  日志 → 全过程审计追溯
```

**关键洞察：** 各层之间的接口性质不同：
| 接口 | 性质 | 风险等级 |
|------|------|---------|
| 数据层→编排层 | 上下文注入 | 中 |
| 编排层→执行层 | 只读vs写入的判断 | 最高 |
| 执行层→区块链 | 发送交易 | 高 |

"变化轨迹管理"应该是一个**跨层的约束层**，不是在单一层内解决的问题。

### 2. RPC 的本质

**第一性原理：** 程序 A 想调用程序 B 的函数，但 A 和 B 不在同一台机器上。RPC 屏蔽了"远程"这个事实。

区块链中的 RPC：
- 以太坊走 JSON-RPC 协议
- 读操作免费（eth_getBalance），写操作付 Gas（eth_sendRawTransaction）
- 类比：RPC 是 dApp 到链的通信层，MCP 是 LLM 到工具的通信层（MCP = RPC + 模型友好的接口描述）

---

### 3. 索引器（Indexer）

**要解决的问题：** 区块链的数据结构是为追加写入优化的，不是为查询优化的。查"某个地址过去30天的全部Swap"如果扫链不可行。

**解决方案：** 逐块读取交易和事件 → 解析/过滤/转化 → 存入可查询数据库

| 工具 | 场景 |
|------|------|
| The Graph | 去中心化索引协议，subgraph |
| Dune Analytics | SQL 查询面板，数据分析 |
| 自建索引器 | 自己的 dApp 需要实时查询 |

**产品意义：** Agent 不是直接读链的，而是通过索引器读链的。索引器是 Agent 的"链上记忆"。

---

### 4. 预言机（Oracle）

**要解决的问题：** 区块链是封闭的确定性系统，不能访问链外。但链上合约需要链下数据（ETH 价格）。

**核心矛盾：**
```
区块链要确定性 → 不能直接访问链外
链上应用需要链外数据 → 需要中间人
中间人 = 预言机 → 新的问题：中间人可信吗？
```

这就是**预言机问题（Oracle Problem）**：区块链的安全性被一个中心化的数据入口打破了。解决方案是去中心化预言机（多个独立节点各自取数据，聚合）。

### 5. 安全层详解

#### Guard（守卫）
操作执行前的第一道拦截。检查白名单、额度限制、操作类型、上下文安全。**必须是代码层的确定性检查，不是 LLM 自我判断。**

#### Simulation（模拟/预览）
在发送有副作用的交易前，先在本地/测试网模拟执行，预览结果。区块链交易不可逆，所以要先看结果再决定。

#### 权限策略（Policy）
可配置的规则引擎，定义 Agent 能做什么、不能做什么、什么条件下可以做。
```
只读操作 → 自动执行
写入操作 → 需 Policy + 人工确认（分额度等级）
紧急操作 → 禁止 / 仅 Owner
```

#### 人工确认（Human-in-the-Loop）
关键写入操作必须等真人拍板。你的分层的关键洞察：编排层→执行层之间，有些步需要插一个人。

#### 日志（Audit Log）
全过程记录：编排层决策 → Guard 结果 → 人工确认 → Simulation 结果 → 执行层操作 → 链上确认。用于事后审计、行为分析、Policy 优化、安全事件响应。

### 6. Prompt 四段式

```
① 任务目标 → ② 可用输入 → ③ 禁止行为 → ④ 输出格式
```

第四段（输出格式/结构化输出）最重要——让 LLM 输出变成可检查对象，后续 Guard 可以直接校验。

**Schema = 数据的结构说明书。** 规定了字段名、类型、是否必须、值域。让 LLM 的自然语言输出变成后续代码能确定性地处理的格式。

### 7. Citation + Freshness

你的核心观察：
> "没有 citation 和 freshness 的 RAG，只是把幻觉从模型内部搬到了检索系统里"

**Citation（引用溯源）：** 答案必须标注来源编号，且每个来源必须在检索结果中出现过。代码可以校验——如果引用不存在，拒绝回答。

**Freshness（时效性）：** 检索回来的信息有多老？每篇文档带 last_updated metadata，检索时语义匹配 + 时间过滤并行。不处理 freshness，新旧文档矛盾时 LLM 会随机选一个。

### 8. Chunk vs Token

| | Token | Chunk |
|---|---|---|
| 属于哪个系统 | LLM 内部（模型推理） | RAG 外部（检索系统） |
| 为什么存在 | 模型只能理解 token 序列 | 文档太大不能直接向量化 |
| 切分依据 | Tokenizer 词汇表（算法决定） | 按段落/标题/语义（人设计） |
| 切错了的后果 | 几乎没有 | 严重——语义碎了 |

你的类比：**Token = 精细肉丝，Chunk = 大块猪腿肉。** Token 是模型的呼吸单位，Chunk 是检索系统的管理单位。

### 9. Agent 的本质

你的判断（极简且正确）：
> **Agent = 赋予了权限的 LLM。LLM 之所以问一句回一句，就是没权限。**

LLM 默认权限只有一项：说话。Agent = LLM + 权限扩展 + 循环执行权。

| | LLM | Agent |
|---|---|---|
| 权限 | 只能说话 | 读/写/执行/循环 |
| 过程 | 问一句答一句 | 目标驱动，多步循环 |
| 状态管理 | 每次对话独立 | 跨步骤追踪 |
| 错误处理 | 你发现错了重问 | 自己发现错了重试 |

**Frameworks（LangChain / LangGraph / DSPy）** 是帮实现 Agent 的脚手架，不是 Agent 本身。先设计 Agent 再选框架。

### 11. LLM 蒸馏

**传统蒸馏：** 教师模型的概率分布作为训练目标教给学生。学生学到的是教师的判断边界和不确定度。

**LLM 黑盒蒸馏（最常见）：** 用强模型 API 生成大量 Q&A 对 → 在这些数据上微调开源模型。这本质上是**模仿**，不是真正的蒸馏，因为拿不到教师的概率分布和中间层。

**关键限制：** 蒸馏模型不可能超过教师——学生是在教师的"影子"里训练。教师的所有错误都会被学生继承。

4. 为"变化轨迹管理"找到了架构位置：跨层的约束层

### 关于权限的认知闭环

从 Agent 推出来的认知线：
```
LLM 只有说话的权限
→ Agent 给它扩展了权限（读/写/循环/执行）
→ 给多少权限 = Policy 的定义
→ 权限边界的执行 = Guard + Simulation + 人工确认
→ 权限使用的记录 = 日志
```

这整个链条就是你 Day 1 那个"收买守卫"类比的技术实现方案。
